# 이슈 기반 AI 개발

Money Flow의 [AI development 워크플로](../.github/workflows/ai-development.yml)는 기본 브랜치인 `dev`에서 실행됩니다. 개발과 리뷰 단계는 [ai-native의 자동화 지침](https://github.com/han41858/ai-native/blob/16eb8b0655251017a04e0bdc7f8ab5b2afee930d/docs/ai-automation.md)을 따르며, 모델 호출과 편집 검증 모듈은 [Agentopia](https://github.com/han41858/agentopia/tree/39013e0358ab41419c96836cff0eb341aa10f77b/.github/scripts/ai-development)에서 가져와 프로젝트에 맞게 조정했습니다. Videx와 Commit Trail의 이슈 승인, 격리 검사, 상태 관리 방식도 참고했습니다.

## 활성화

1. 워크플로 PR을 `dev`에 머지합니다.
2. 저장소의 **Settings → Environments**에서 `ai-development`를 만들고 **Deployment branches and tags → Selected branches and tags**로 설정합니다. 허용 규칙에는 `dev` 브랜치 한 개만 등록합니다.
3. 해당 Environment에 비밀과 변수를 설정합니다.

   | 종류     | 이름                  | 용도                                                                                                                             |
   | -------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
   | Secret   | `OPENAI_API_KEY`      | Codex 모델의 Responses API                                                                                                       |
   | Secret   | `ANTHROPIC_API_KEY`   | Claude 모델의 Messages API                                                                                                       |
   | Secret   | `AI_AUTOMATION_TOKEN` | 이 저장소에만 접근하는 GitHub App 또는 fine-grained PAT. Contents, Pull requests 쓰기 권한으로 브랜치·커밋·초안 PR을 게시합니다. |
   | Variable | `AI_CODEX_MODEL`      | OpenAI 계정에서 사용할 수 있는 Codex 모델 ID                                                                                     |
   | Variable | `AI_CLAUDE_MODEL`     | Anthropic 계정에서 사용할 수 있는 Claude 모델 ID                                                                                 |

   `AI_AUTOMATION_TOKEN`은 후속 `pull_request` CI 이벤트가 발생하는 자격 증명이어야 합니다. 실행 기록과 리뷰 댓글, 준비 완료 전환, 머지, 이슈 종료에는 각 job의 권한으로 제한한 `GITHUB_TOKEN`을 사용합니다.

4. **Settings → Rules → Rulesets → dev**에서 필수 검사 `verify`와 **Require branches to be up to date before merging**을 활성화합니다. 저장소의 [dev 룰셋 정의](../.github/rulesets/dev.json)와 일치해야 합니다. 그래야 머지 직전 다른 PR이 반영돼도 GitHub가 이전 기준의 CI로 머지하는 것을 막습니다. Environment와 룰셋 설정은 워크플로에서 다시 확인합니다.

## 사용

- 작업과 완료 조건이 적힌 이슈에 저장소 쓰기 권한이 있는 사람이 `ai:develop` 라벨을 붙입니다. 이슈 생성 시 붙이거나 나중에 붙이거나 라벨 부착 이벤트(`issues.labeled`) 한 번으로 개발을 시작합니다. 라벨은 자동 개발, `dev` squash merge 및 이슈 종료의 승인입니다. 하나의 이슈에 하나의 작업 브랜치와 초안 PR을 사용합니다. 중단하려면 승인 라벨을 제거하거나 `ai:stop`을 붙입니다.
- Codex가 `src/`, `tests/`, `docs/`, `README.md`의 허용된 텍스트 파일을 수정합니다. 숨김 경로와 도구 설정 파일은 자동 편집에서 제외합니다. 워크플로, 자동화, 의존성 및 도구 설정 변경은 수동 PR로 진행합니다. 파일에 적용한 변경은 자격 증명과 네트워크를 제공하지 않는 Docker에서 포맷, 타입, 린트, 단위 테스트, 빌드, Chromium 검사를 통과한 뒤 게시합니다. 격리 환경은 Chromium이 한글 다운로드 파일명과 프로필 경로를 처리할 수 있도록 UTF-8 로캘을 사용합니다.
- Claude가 같은 HEAD의 변경과 관련 테스트를 독립 검토합니다. 실행기는 게시된 커밋과 검증 후보의 파일 트리가 일치하는지 확인하고, 검토 커밋·격리 검사 실행 링크·관련 Chromium 결과를 전달합니다. Claude는 결함 수정 요청, 추가 검증, 사람 판단 요청을 구분합니다. 추가 검증이나 사람 판단이 필요하면 이슈 종료 댓글에 확인할 내용과 리뷰·검사 링크를 남깁니다. 수정 요청은 Codex가 같은 PR에서 최대 두 번 보완합니다. 승인된 현재 HEAD의 `verify`가 성공하고 승인, 브랜치, PR이 유효하면 `dev`에 squash merge합니다. 머지 커밋이 `dev`에 들어갔고 이슈가 완료 상태인지 각각 확인합니다.
- 작업 기록이 있는 이슈에 승인 라벨을 다시 붙이면 Actions 로그에 기존 상태를 표시하고 중복 실행을 건너뜁니다. 모델을 호출하기 전 준비 단계에서 실패했고 작업 브랜치가 없다면, 변경하지 않은 이슈에 승인 라벨을 다시 붙여 한 번 재개할 수 있습니다. 후보가 격리 검사에서 실패했고 브랜치를 게시하지 않았다면 같은 방식으로 검사 실패를 한 번 재개할 수 있습니다. 실패한 검사 단계는 이슈에 기록합니다. UI 테스트 본문 확인에서 멈췄고 변경을 게시하지 않은 이슈도 같은 방식으로 한 번 재개할 수 있습니다. 판별 가능한 검사 오류가 나면 이전 변경 후보를 실행기 내부에 보존하고 Codex에 실패 진단을 전달합니다. 다음 회차는 그 후보를 읽어 필요한 수정분만 제출하고, 실패한 검사부터 다시 실행합니다. 전체 개발 횟수 한도를 공유합니다. 후보는 전체 검사를 통과할 때까지 브랜치나 PR에 게시되지 않습니다. 실행이 끝나면 보존 범위도 끝납니다. 검사가 시간 또는 출력 한도를 넘으면 그 사유를 기록하고 보완하지 않습니다. GitHub 읽기 요청의 일시적 전송 실패는 제한적으로 다시 시도합니다. CI 대기가 시간 한도에 도달하면 댓글에 재개 방법을 기록하고 Actions 실행을 실패로 표시합니다. 이 경우나 종료 요청이 중단된 경우에는 Actions에서 `dev`의 **AI development**를 이슈 번호로 수동 실행해 검증·종료 단계만 재개할 수 있습니다. CI가 실패하면 로그를 확인하고 동일 HEAD의 검사를 다시 실행할 수 있습니다. 기준·이슈 범위·작업 HEAD가 바뀌거나 리뷰 보완 한도에 도달하면 이슈와 PR에서 수동으로 이어갑니다. Codex가 사람의 판단을 요청할 때 기존 작업 PR이 있으면 종료 댓글에서 바로 연결합니다.
- 후보에서만 고쳐야 하는 브라우저 실패인지 확인할 때는 변경된 테스트와 이슈의 재현 검사를 제외합니다. 나머지 실패 사례를 같은 격리 환경에서 수정 전 기준 커밋으로 재실행해 파일·제목·오류가 모두 일치하면 기준 검사 실패 상태로 중단합니다. 모델 보완 회차를 추가로 소모하지 않습니다. Actions 로그의 `validation_repair`에는 회차, 실패 단계, 후보 파일 수를 남깁니다.
- 이슈 댓글은 작업 중, 리뷰 중, CI 대기·실패, 사람 확인, 머지됨, 완료 상태를 표시합니다. 이슈마다 진행 댓글 하나를 갱신합니다. 상단에는 최신 실행의 회차, 현재 상태와 필요한 조치를 표시하고, 아래에는 시작·리뷰·CI 실패·재개·병합·완료를 펼친 시간순 목록으로 남깁니다. 재실행은 별도 회차로 구분하며 각 회차의 Actions 링크와 관련 PR·리뷰 링크를 보존합니다. 같은 이슈의 실행은 GitHub Actions의 동시 실행 그룹에서 직렬화하고, 실행기 안의 댓글 갱신도 이슈별로 순서대로 처리합니다. 같은 회차의 동일 기록은 한 번만 쓰고, 늦게 도착한 이전 결과는 이전 회차에만 추가합니다. 댓글 길이 한도에 가까워지면 오래된 회차부터 줄이고, 댓글에 줄인 회차 수와 해당 Actions 링크를 표시합니다. 자동화의 상태 확인은 댓글 상단 문구나 과거 기록 대신 최신 실행의 상태 체크포인트를 읽습니다. 기존 이슈의 진행 댓글은 다음 갱신 때 재사용하며 이전 댓글을 삭제하지 않습니다. Claude의 상세 리뷰는 검토한 커밋별로 PR에 남깁니다. Actions 로그는 모델 호출 시간·사용량과 검사 단계를 표시합니다. 기존 Vercel `preview` 라벨 정책과 `main` 승격 절차를 따릅니다.

### 후속 이슈와 병합 후 정리

- 후속 이슈 본문에 `선행 이슈: #123`을 한 줄씩 적습니다. 각 선행 이슈가 완료로 닫혔고 연결 PR의 머지 커밋이 `dev`에 포함된 것을 확인할 때까지 모델을 호출하지 않습니다. 예약 실행은 30분 간격으로 대기 이슈를 확인합니다. 원래 이슈 본문과 관리자 승인 라벨이 유지된 경우에만 최신 `dev`에서 후속 개발을 시작합니다. 재개 직전에 `dev`가 갱신된 경우 최대 두 번 다시 대기합니다. 환경이나 브랜치 등 다른 조건에 막히면 이슈 댓글에 이유를 남기고 예약 재시도를 멈춥니다. 문제를 해결하거나 대기 중 요구사항을 편집한 뒤 `ai:develop` 라벨을 다시 붙여 승인합니다. PR 없이 완료로 닫힌 선행 이슈는 병합을 확인할 수 없으므로 대기합니다.
- 자동 병합과 이슈 종료를 확인한 뒤, 저장소 설정이 켜져 있으면 해당 `ai/issue-*` 브랜치를 정리합니다. 열린 PR이 사용하는 브랜치는 보존하고, 원격 HEAD가 병합 당시와 같을 때만 삭제 요청을 보냅니다. 정리 결과는 완료 댓글에 기록합니다.
- 관리자가 작업 PR을 수동 병합하면, 머지 커밋이 `dev`에 있고 이슈가 완료로 닫힌 것을 확인해 진행 댓글을 갱신합니다. 이미 병합된 이슈의 댓글은 `phase: sync`로 다시 확인할 수 있습니다.

### Claude 리뷰 재개

Claude가 리뷰 중 추론 블록이나 서명을 이유로 HTTP 400을 반환하면, 실행기는 읽기 결과를 유지하면서 서명 블록이 없는 요청으로 한 번만 다시 시도합니다. 이후에도 같은 오류가 나면 실행을 멈추고 이슈에 남깁니다.

이 오류로 이미 게시된 PR은 저장소 관리자가 `dev`의 **AI development**를 이슈 번호와 `phase: review`로 실행해 재개할 수 있습니다. 승인 라벨, 원래 이슈 내용, 작업 브랜치 및 PR을 확인합니다. `dev`가 앞서면 충돌이 없는 기준 갱신만 허용하고, 갱신된 HEAD에서 격리 검사와 Claude 리뷰를 다시 실행합니다. 리뷰가 승인되고 같은 HEAD의 필수 CI가 통과하면 기존 완료 단계가 병합과 이슈 종료를 처리합니다. 충돌을 직접 해결한 뒤에는 `phase: review`와 `expected_head`에 PR의 정확한 전체 SHA를 지정합니다. 해당 커밋이 최신 `dev`를 포함하고 허용된 제품 파일만 변경했는지 확인한 뒤 전체 검증과 Claude 리뷰를 수행합니다. `phase: complete`는 이미 승인된 PR의 CI·종료 재개에 사용합니다.

### UI 이슈 재현 검사

이슈에 재현에 필요한 초기 데이터, 대표 금액 또는 입력, 화면 너비, 조작 순서, 기대 결과를 적습니다. 예를 들어 자동 정렬 이슈에서 금액이 겹치지 않는지, 연결 포트를 조작할 수 있는지, 금액을 직접 편집할 수 있는지, 좁은 화면에서 배율이 맞는지를 각각 확인합니다.

기존 또는 추가할 Playwright 검사의 파일과 정확한 테스트 제목을 알고 있다면 이슈에 아래처럼 지정합니다.

```markdown
## UI 재현 테스트

- tests/editor.spec.ts | 자동 정렬 후 합류·분기 금액이 겹치지 않는다 (390px)
```

지정한 검사는 개발 전에 기준 커밋에서 먼저 실행합니다. 새 재현 검사가 필요하면 후보의 대상 테스트와 `tests/`의 지원 파일 변경을 기준 커밋에 적용해 제품 변경 없이 단언이 실패하는지 확인합니다. 이 트리에서 빌드가 실패하면 UI 재현 단계 실패로 구분하고, 컴파일 진단을 다음 보완 회차에 전달합니다. 지정 항목이 없는 UI 변경은 후보가 추가하거나 수정한 브라우저 검사에서 재현 근거를 찾습니다. 기준에서 재현된 검사가 후보의 전체 검사에서 실제로 통과해야 게시할 수 있습니다. 재현 테스트와 지원 파일에서 사용하는 제품 API는 기준 커밋에서도 사용할 수 있어야 합니다.

개발 및 리뷰는 각각 최대 15 모델 턴을 사용하고, 모델 요청 한 건은 최대 3분입니다. 완료나 승인 결과를 냈지만 UI 테스트 본문을 읽지 않은 경우, 해당 본문을 읽는 요청과 최종 결과 요청을 각 한 번 추가합니다. 본문 확인이 실패하면 게시나 승인 없이 중단합니다. Codex 개발 응답이 12,000 출력 토큰에서 잘리면 해당 개발 회차에서 한 번만 같은 요청을 18,000 출력 토큰과 최대 4분으로 다시 시도합니다. 개발 job은 65분, 완료 job은 23분으로 제한됩니다. 의존 이슈 큐, 자동 기준 복구·충돌 해소, CI 실패 자동 수정은 초기 범위에서 제외합니다. 새 기준이나 CI 실패에 대한 수정이 필요한 경우 사람이 이어갑니다. 실제 운영 전에는 토큰과 Environment를 설정한 뒤 작은 이슈로 모델 호출부터 이슈 종료까지 확인하세요.
